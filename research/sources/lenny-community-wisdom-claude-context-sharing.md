## Relevance to the project
One thread in this digest ("Backing up Claude Code context and sharing it across a team") is a compact snapshot of how practitioners in mid-2026 were trying to move file-based agent context from one person's laptop to a team: shared Git repos of skills, templates and context with PR approval and symlinks; Obsidian; Google Drive shared folders; homegrown "context systems". The most useful contribution is a practitioner's list of why plain shared file storage fails for agent context: you can't tell who changed what, why, what is trustworthy, or lock files you worked hard to get right. It bears directly on context-and-memory, artifact-and-project-structure, capability-distribution-trust and target-user (non-technical colleagues for whom GitHub is "overwhelming"). Only threads 5 and a line from thread 1 are relevant; the rest (fractional CPO pay, e-signature tools, unused subscriptions, referral terms) are not.

## Themes
- compounding-context-repo / skills-marketplace: a person newly hired "to operationalize AI across our teams" describes a shared repo to publish skills, templates and context files; anyone can submit a change but "it has to be approved as a PR in GitHub"; symlinks keep everyone current; goals: avoid duplicate work, encourage sharing, and "some governance so not just anything gets pushed" (thread 5).
- scoped-governance-containers / memory-architecture: a builder whose team left Obsidian because it lacked collaboration and had "too little governance around what agents can do to the data (without a human in the loop)"; shared file stores can't show who changed what or why, which context is trustworthy ("folders help, till the content in those folders gets polluted"), or protect finished files; they are building their own context system (thread 5).
- artifact-standardization: a 17-person company's CEO wants everyone on Claude Pro pointed at shared strategic priorities, a knowledge library and templates "for consistency and quality of outputs", plus a weekly team stoplight (risk) report that needs read and write access to shared locations (thread 5).
- harness-portability: a member in a large organisation runs a team "operating system": Claude Code with shared settings, scripts and dockerised API providers for Copilot and internal Bedrock models, shared skills in a GitHub repo plus personal ones, per-repo instructions; MCP servers kept mostly disabled because "they tend to eat too much of the context"; no good context-sharing system yet (thread 5).
- non-engineer-builders: most of the 17-person org are execs, consultants, program managers and ops staff, "all non-technical", using chat in the browser; GitHub would overwhelm them, so Google Drive sync is being considered (thread 5).

## Key points
- Personal setups: Obsidian as the store for plans and documents, machine backups, a homegrown macOS sync of skills and sessions between two machines (thread 5).
- Two members mention emerging formats or tools (llm-wiki, a Google "open knowledge format" spec, and a member's own memory tool with a draft-then-promote "quality gate" lifecycle). These are self-promotions or unverified pointers, recorded here only as signals of demand.
- Thread 1 aside: a fractional product lead says the role is often "trying to enforce product discipline" when a founder is "PR-happy because Claude tells them all ideas are wonderful".
