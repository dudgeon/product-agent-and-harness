## Relevance to the project
Anthropic's own end-to-end design for an AI-native product loop: every stage commits a markdown or code artifact (intent.md, spec.md, plan.md, the diff, the PR review, the incident record) that the next stage reads, so the chain of commits is both the workflow and the audit trail. It is the most explicit vendor version yet of the project's opportunity-to-code chain, and it puts a product owner (not an engineer) at the top: any employee writes intent with Claude in claude.ai or Cowork, and the product owner reviews an agent-written spec rather than writing one. It also gives a concrete, regulated-enterprise control set (skills as advisory policy, hooks as deterministic gates, managed settings, evals on the agent's own configuration), which bears on the review-and-autonomy, governance-control-plane, intent-shaping-and-spec and artifact-and-project-structure dimensions. Treat it as first-party prescription drawn from "working with our customers", with no outcome data: its measures are proposed indicators, not results.

## Themes
- opportunity-to-code-chain: the chain is intent.md → spec.md → plan.md → diff and tests → PR with findings → incident record → new intent.md; "each stage ends by writing one to version control ... and the next stage begins by reading it" (§What is an AI-native SDLC). It starts at intent: problem and proposed outcome are fields inside intent.md, so the opportunity/problem/goal stages the Stripe chain keeps human are folded into one originator-written artifact (§Stage 1).
- agent-factory-sdlc: six stages (Plan, Design, Build, Test, Deploy, Maintain) with an agent embedded in each and a loop, not a line; the end state is "a loop in which each accepted artifact fires the next gate" (§Plays).
- docs-as-code-prd: intent and spec live as markdown in an `intent/` folder in the product repo for a single product; a dedicated intent repo only when intent spans many repos (§Stage 1, Infrastructure).
- agent-ready-intent: an agreed intent.md template, encoded as a skill "set up by a technical team member and signed off by a lead" (§Stage 1, How to execute).
- agent-led-intent-shaping: Claude "asks the questions an analyst would ask: scope, users, constraints, and what success looks like" while the originator brainstorms; the spec pass must flag "areas of concern, especially where you cannot satisfy contradicting policies" (§Stage 1, §Stage 2 prompt).
- human-review-gates / risk-sloped-review: humans gate each accepted artifact (product owner accepts intent and spec; engineer accepts plan; code owner approves PR via branch protection); higher-risk changes escalate to a tech lead or architect; human line review is reserved "for regulated and critical code" (§Shifts table, §Stage 3 governance).
- evals-autonomy-trust: continuous evals run in CI on any change to CLAUDE.md, skills or hooks, because "that configuration steers the agent and deserves the regression testing that code gets"; 20 to 50 real tasks to start; every incident becomes an eval (§Stage 4).
- enterprise-admin-controls: a worked managed-settings file for a regulated enterprise (deny reads of secrets, OS sandbox with domain allowlist, managed hooks and MCP servers only, an approved plugin marketplace, a minimum version) (§Stage 5, Worked example).
- compounding-context-repo / org-learning-loop: "When Claude makes a mistake twice, the correction goes into CLAUDE.md"; review findings feed CLAUDE.md; incidents feed evals; post-mortems go to a lessons file (§Stage 3, §Stage 5, §Stage 6).
- artifact-standardization: named artifacts per stage with templates (intent.md, spec.md, plan.md, REVIEW.md, bands.yaml) (throughout).

## Key points
- **Premise (§Code is no longer the bottleneck).** Build has collapsed to hours; plan, review/test and deploy still run "at human speed"; per-line human review cannot keep up once agents write most of the diff; governance by committee adds cost. The fix is to rebuild the stages around agents while keeping the old control objectives.
- **Stage 1, Plan: capture as intent.md.** Intent enters from a person's idea, a ticket, or an alert from monitoring. The originator brainstorms with Claude and gets a "proto-spec" in their own words (problem, proposed outcome, affected users and systems, constraints, open questions). Non-engineers use claude.ai or Cowork; a version-control connector lets Claude commit the file for them, so they never touch git. The product owner reviews and corrects before commit; accept/reject is recorded as merge or closed review. Proposed measures: time from first conversation to committed intent (expected to fall "from a multi-week elicitation and refinement cycle to hours"), and the "survival rate" of intents accepted into design.
- **Stage 2, Design: requirements and design in one session.** Claude turns the accepted intent into spec.md under the organisation's skills for brand, security, compliance and UX; "the product owner reviews that spec, but doesn't write it". Flagged concerns go to named policy owners before engineering sees the spec. Run by hand first, then as an org slash command, then as a non-interactive job triggered by the intent merge that opens spec.md as a PR. Front-end work goes via Claude Design to Claude Code. Measures: intent-to-spec elapsed time; spec commits after the first plan.md commit (requirements rework).
- **Stage 3, Build.** Plan mode by default: Claude reads the codebase without editing, interviews the engineer, and the approved plan is committed as plan.md, which the later PR review checks the diff against. Auto mode for routine work once guardrails mature. CLAUDE.md kept under a page. Skills as "institutional knowledge" with a named policy owner who signs off changes; a skill is "a control, though an advisory one", so policies that must always hold need a hook behind them. Parallel sessions in git worktrees (start with two or three; ceiling is how much one person can review) and subagents defined in `.claude/agents/`.
- **Sidebar: legacy systems and the source of truth.** For each artifact, name one system of record: the repo (markdown authoritative, legacy tools link to commits), the legacy tool (Jira, ServiceNow or a requirements tool authoritative, Claude reads and writes it via MCP in the same session), or, as the minimum, two-way linkage (record ID in the file, commit SHA in the record). This is the playbook's answer to regulated orgs whose auditors already accept Jira or a traceability tool.
- **Stage 4, Test.** Give every session a self-check (tests, build, screenshot diff); write the failing test first for bug fixes and block the agent from editing tests with a hook. Continuous evals in CI (example GitHub workflow runs `claude -p` over eval prompts on PRs touching CLAUDE.md or `.claude/**` and nightly); configuration changes that drop the pass rate get reviewed before merge.
- **Stage 5, Deploy.** All PRs get identical agent review passes (bugs, security, compliance against spec.md and plan.md) defined in a REVIEW.md, with severity tiers and a nit cap; findings never approve or block on their own; branch protection still needs a code owner. The authoring agent cannot approve its own code ("separation of duties is preserved"). Hooks can allow, ask or block; team hooks in `.claude/settings.json`, non-negotiable ones in managed settings. Agent jobs run sandboxed with short-lived tokens and no standing production credentials; deploy, status and rollback are exposed as MCP tools scoped per environment; autonomy is tiered by environment (free in dev, prepared-but-human-authorised in production). Principle: "the agent may act up to the production gate and cannot pass it."
- **Stage 6, Maintain: closing the loop.** A deterministic detection script (rolling baseline, Western Electric rules, no model) watches a metric; tiers in a versioned bands.yaml: log at 1σ, read-only diagnosis at 2σ, act at 3σ only by opening a PR or triggering a pre-approved runbook. The agent writes its diagnosis as a new intent.md, so "a loop can begin and end without anyone starting it". People triage the queue rather than start the work. Also: recurring scheduled security scans (Claude Security, Enterprise public beta) whose findings go through the same PR gate or become intent.md; and Claude Tag in Slack as on-call first responder, with the channel as the audit trail.
- **Measurement throughout.** Each play names a leading and a lagging indicator read from git, PR metadata, CI, an OpenTelemetry export or the incident tracker (e.g. first-pass CI success, review time per PR, DORA measures, share of findings that become merged fixes). None are reported as achieved results.
- **Adoption order.** Plays are modular with a dependency graph; start with any play that has no prerequisites (intent capture, CLAUDE.md, skills, hooks as gates, feedback loop). Prompt each step by hand first; automate the triggers later.
- **Limits.** No customer outcomes, costs or failure cases are given; several products it relies on are beta (Claude Design, Claude Tag, Claude Security); everything assumes Anthropic tooling (Claude Code, managed settings, Code Review, Claude Tag), though the artifact chain itself is tool-neutral.
