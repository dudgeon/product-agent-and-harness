Where Atlassian’s agents sit in the product lifecycle, task by task

Same frame as the Stripe map. Rows are tasks, not job titles. Most evidence describes what Atlassian sells (support docs, launch posts); a few sources describe how Atlassian’s own teams work, marked internal. Each handoff is marked documented, inferred or unknown. Every figure is Atlassian’s own.

The work item carries the what, not the why

Atlassian has an object at every step (idea, goal, spec, work item, pull request) and links between most of them. Context breaks between research and the first shaped artifact, and in what a work item copy leaves out.

  1. Research output stays in chat. Rovo Deep Research writes a cited report in Rovo Chat; export to Confluence is claimed only in a 2025 blog. Customer insight is triaged by agents, but the documented outputs are bugs and updates to existing work items, not new ideas or specs.
  2. What crosses from intent to plan is a copy. A product discovery idea links to delivery work, and its owner may embed the idea’s description in the work item. That is the only documented way idea content reaches the item an agent reads; the insights stay behind the link.
  3. The coding agent reads the work item; linked documents are conditional. Started by automation it “won’t read Confluence content”. Whether it follows links by default is not stated.
  4. The bridge being built is a spec, and it’s early. Jira Planner (Early Access) turns a rough idea into a Confluence spec, then into work items with acceptance criteria. Whether it reads ideas, goals or research is not stated.
  5. The graph links pairs; nothing ties the chain. Teamwork Graph returns a work item’s pull requests, pages and parents, but no record joins research → idea → spec → work item → PR.

Across people: on small teams (Confluence, Rovoclaw) one person researched, shaped and prototyped, so context travelled with them. On Jira, where PMs did not commit to production, Atlassian made the PM’s intent executable instead: a Loom talk track became work items, moving one to In Progress started a cloud coding agent, and the prototype landed in the real repo, so “the handoff to developers was much faster”. That carries the prototype across people, not the evidence behind it.

Against Stripe: Stripe’s research agent is locked in single-user sessions and its planner starts from typed intent. Atlassian has the shared, linked objects Stripe lacks, so its gap is narrower, but it sits in the same place.

What a work item carries, and what it doesn’t

  • Carries: summary, description and acceptance-criteria fields (which the reviewer reads); links to an idea, a goal, pages and pull requests; an embedded copy of the idea’s description if its owner chose to embed; the agent sessions and the draft PR.
  • Doesn’t carry: the research behind the idea; the shaper’s reasoning (Loom keeps the video, but only action items become work items); review feedback back to the agent (manual today); Confluence content for agents started by automation. And a link is not a read.

What it means for our options

  • The work item is the handoff contract, and it is harness-agnostic at the code step. Five coding agents take the same item and the reviewer checks the same acceptance criteria. That favours a product agent that writes into the system of record over one that holds intent in its own sessions.
  • Copy intent into the artifact the next agent reads; don’t rely on links. The idea “embed” option and the reviewer’s empty-description rule say the same thing.
  • The seam to fund is still research → first shaped artifact. Atlassian has the objects; it has no documented path from research output into them.
  • Who may write code is a per-codebase choice. PMs committed on Confluence (isolated repo, explicit contribution model) and not on Jira.
