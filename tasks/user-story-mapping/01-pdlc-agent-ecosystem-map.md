# Atlassian's agent ecosystem, mapped to the tasks of the product lifecycle

Date: 2026-10-24. Same frame as the [Stripe map](../competitive-teardown-stripe-knowledge-agents/02-pdlc-agent-ecosystem-map.md). Built only from filed source notes in `../../research/sources/`; detail per task is in [research-atlassian-sdlc-agents.md](research-atlassian-sdlc-agents.md). Each handoff is marked **documented** (an Atlassian or independent source says it happens), **inferred** (consistent with the sources but not stated) or **unknown**. Visual version: [01-pdlc-agent-ecosystem-map.html](01-pdlc-agent-ecosystem-map.html).

## Two kinds of evidence, kept apart

Atlassian is a platform vendor, so most sources describe **product capability** (support docs, first-party; launch blogs and guides, vendor claim). Only a few describe **how Atlassian's own teams work**: the CPO's Lenny & Friends talk ([transcript](../../research/sources/lenny-podcast-tamar-yehoshua-roles-expanding.transcript.md), first-party, speaker-reported, auto-captions), one engineer's account of Rovo Dev in Jira ([note](../../research/sources/atlassian-blog-rovo-dev-in-jira.md), related post), and Atlassian's own PR-review figures ([note](../../research/sources/arxiv-rovodev-code-reviewer-icse26.md)). In the tables, *internal* marks the second kind. The Stripe map is almost all internal use; this one is mostly product. A cross-ecosystem comparison should not read a documented product feature as evidence that Atlassian's teams use it.

## Why tasks, not job titles, here too

- **Roles blur by design on small teams.** On Confluence, a PM who had never coded "ended up checking in 26 PRs in a month" through a harness an engineer built and "a clean isolated repository"; the team set "a very intentional contribution model of who was going to do what" ([transcript](../../research/sources/lenny-podcast-tamar-yehoshua-roles-expanding.transcript.md) 06:32–09:32). On Rovoclaw, a PM and a designer "vibe coded the whole thing" to an alpha before engineers joined (10:02).
- **They don't blur on the big codebase.** On Jira, "PMs did not check in code to the production environment" (16:03); PMs prototyped and steered.
- **Atlassian frames the lifecycle around the work item, not the role.** Its agentic-engineering guide: "Set the goal (people decide what and why; Jira turns it into a plan)", then assign the work item to an agent ([guide](../../research/sources/atlassian-jira-agentic-engineering-guide.md), vendor claim).

So each row is a task, and "who does it" lists the roles the sources show.

## The short answer: where context breaks between research, intent and plan

**The work item is the handoff medium, and it carries the *what*, not the *why*.** Atlassian has an object at every step and links between most of them, but the research and its reasoning have no documented path into the idea, spec or plan.

1. **Research output stays in chat.** Rovo Deep Research produces a cited report in Rovo Chat ([note](../../research/sources/atlassian-rovo-deep-research.md)); export to Confluence is claimed only in a 2025 engineering blog, not in the support doc. Customer insight is triaged by agents (900+ items categorised, internal) but the documented outputs are bugs and updates to *existing* work items, not new ideas or specs ([Loom note](../../research/sources/atlassian-loom-record-for-agent.md); [transcript](../../research/sources/lenny-podcast-tamar-yehoshua-roles-expanding.transcript.md) 15:03–15:33). No source describes research flowing into a JPD idea, a PRD or a plan.
2. **What crosses from intent to plan is a copy.** A JPD idea links to delivery work items, and the owner may "embed the idea description and fields into the work item" ([JPD link note](../../research/sources/atlassian-jpd-link-idea-to-work-item.md), first-party). That is the only documented way idea content gets *inside* the item an agent reads. Insights attached to the idea stay behind the link.
3. **The coding agent reads the work item; linked documents are conditional.** Interactively it can read Jira and Confluence as the user; started by automation it runs in a "restricted mode" that "won't read Confluence content" ([coding agent note](../../research/sources/atlassian-jira-coding-agent-generate-code.md), first-party). Whether it reads linked pages and comments by default is not stated.
4. **The bridge Atlassian is building is a spec, and it's early.** Jira Planner turns a rough idea into a Confluence Live Doc spec through clarifying questions, then into work items "each one carrying its own acceptance criteria", reading code and "context from Teamwork Graph" ([Planner note](../../research/sources/atlassian-blog-introducing-jira-planner.md), vendor claim, Early Access). Whether it reads JPD ideas, goals or research pages is not stated.
5. **The graph links pairs; nothing ties the chain.** Teamwork Graph returns a work item's "related pull requests, commits, branches, pages, and hierarchy" ([Delivery Agent note](../../research/sources/atlassian-rovo-jira-delivery-agent.md), first-party), and there are typed edges such as work item → goal ([Goals note](../../research/sources/atlassian-goals-what-is-a-goal.md)). No lifecycle record joins research → idea → spec → work item → PR.

**Across people.** Where one person does research, intent and prototype (Confluence, Rovoclaw), the context travels in that person's head, as at Stripe. Where the tasks split (Jira: PMs shape and steer, engineers ship), Atlassian's internal answer was to make the PM's intent executable rather than to carry the research: a Loom talk track becomes work items, moving one to In Progress starts a cloud coding agent, and the prototype lands "in the actual front-end repository" in the design language, so "the handoff to developers was much faster" (14:03–14:33). That carries the prototype across people; it does not carry the evidence behind it.

**Contrast with Stripe.** Stripe's gap is that Kai's research is locked in single-user sessions and Orbit starts from typed intent. Atlassian has the shared objects Stripe lacks (ideas, goals, specs, work items, all linked), so its gap is narrower but in the same place: between research and the first shaped artifact, and in what a work item copy leaves out.

## What a work item carries, and what it doesn't

Carries (documented): summary, description, acceptance-criteria fields (read by the reviewer), links to a JPD idea, a goal, Confluence pages and PRs; an embedded copy of an idea's description if the owner chose to embed; the agent sessions and the draft PR it produced.

Doesn't carry (documented or not shown): the research behind the idea (Deep Research reports stay in chat unless exported; insights stay on the JPD idea); the reasoning of the person who shaped it (Loom keeps the video and quotes, but only the action items become work items); review feedback back to the agent (manual today); Confluence content for agents started by automation. And a link is not a read: the sources document that the coding agent *can* read Confluence interactively, not that it follows a work item's links by default.

## What it means for our options

- **The work item as the handoff contract is Atlassian's bet, and it is harness-agnostic at the code step.** Any of five coding agents takes the same work item, and the reviewer checks against the same acceptance criteria. That is evidence for a product agent that writes *into* the system of record rather than holding intent in its own sessions ([artifact-and-project-structure](../../options/DIMENSIONS.md#artifact-and-project-structure-how-pm-artifacts-and-projects-are-structured-stored-and-found), platform-owned option).
- **Copying intent into the work item is the reliable path; links are not.** JPD's "embed" and the reviewer's empty-description rule both say the same thing: what the agent sees is what is in the item. A product agent that shapes intent should land evidence and acceptance criteria *in* the artifact the next agent reads (story S05).
- **The seam to build for is still research → first shaped artifact.** Atlassian has objects for ideas, goals, specs and work items, but no documented path from research output into them. That matches the Stripe finding at a different layer ([context-and-memory](../../options/DIMENSIONS.md#context-and-memory-context-and-memory); [intent-shaping-and-spec](../../options/DIMENSIONS.md#intent-shaping-and-spec-intent-shaping-mode-and-spec-standard)).
- **Roles are a per-codebase decision.** Atlassian let PMs commit on Confluence (isolated repo, explicit contribution model) and not on Jira. "Who may write code" is a governance choice per repo, not per title ([target-user](../../options/DIMENSIONS.md#target-user-which-users-and-personas-we-serve-first-including-for-shared-agents)).

Key questions:
1. Does Jira Planner (or any Atlassian agent) read a JPD idea's insights, a goal or a Deep Research report when it drafts a spec, or only what is typed and linked? — *answered by:* an Early Access trial; Atlassian product docs once Planner is GA.
2. In Atlassian's own teams, how does research reach the person who writes the spec when they are different people? — *answered by:* an Atlassian PM interview; a second internal talk or blog.

## Could not verify

- All internal-use claims come from one CPO talk (auto-captions; speaker-reported, no baselines) and one engineer's blog post.
- Jira Planner exists only in a launch blog (Early Access); its inputs are claimed, not documented.
- Whether the Jira Coding Agent reads linked Confluence pages or comments by default; whether third-party agents get Teamwork Graph context without the Rovo MCP server.
- PR cycle-time figures: −30.8% (ICSE paper, all authors Atlassian-affiliated) and −45% (blog) are not reconciled.
- Release: no Compass or deployment-tracking agent found; Pipelines summaries' destination not stated.
- The Rovo reviews (partner, competitor, one team's write-up) report hallucinated summaries and inconsistent backlog analysis ([cbtw](../../research/sources/cbtw-atlassian-rovo-real-world-feedback.md), [slite](../../research/sources/slite-atlassian-rovo-ai-review.md), [devto](../../research/sources/devto-tschimev-why-atlassian-rovo-failed-us.md), all anecdote); none covers the coding or planning agents.
