# The maturity model: crawl, walk, run, on two axes

Date: 2026-10-28. Part of the dependency-agent research (see [00-summary.md](00-summary.md)). This document sets out a maturity model for a dependency agent on two axes: what the agent can do and how much it may do unaided, and how legible the environment is to it. For each stage it says what the agent does, what it needs, what it gives back, and what moves an organisation to the next stage. It then tests the working hypothesis that an early-stage agent in a limited-context environment creates value by driving process standardisation while aggregating and curating context, and that this compounds. The companion page [08-maturity-model.html](08-maturity-model.html) presents the same model. Evidence is in `../../research/sources/`, labelled; the model is this research's design and says where it goes beyond the evidence.

## 1. Why two axes

A single "agent maturity" line hides the thing that matters most in a large regulated organisation: the agent's usefulness is bounded by what it can read and trust, and that is a property of the environment, not the model. The evidence for this is consistent across the research:

- Every shipped planning agent reads only the dependencies people already recorded ([Asana](../../research/sources/asana-ai-teammates-overview-launch-planner.md), [ServiceNow](../../research/sources/servicenow-docs-now-assist-spm-release-notes.md), [monday](../../research/sources/monday-dependency-and-risk-mapper-agent.md)).
- The records are stale by default: half of engineers do not trust their system of record ([Port](../../research/sources/port-state-of-idp-2025-metadata-trust.md), vendor survey); 6.5% of regulatory dependency registers were clean at first attempt ([ESAs](../../research/sources/esas-dora-dry-run-register-of-information.md), regulator).
- Stripe put a bot over its documentation only after owner verification made the documentation trustworthy; the docs complaint then dropped steeply in the next survey ([Stripe panel](../../research/sources/stripe-sessions-2024-10x-engineer-panel.md), first-party).
- Context files that are published are not necessarily read: 97% of llms.txt files got no requests ([PPC Land on Ahrefs](../../research/sources/ppcland-llms-txt-adoption-zero-requests.md), independent).

So the model has an **agent axis** (capability and autonomy) and an **environment axis** (legibility and agent-compatibility of platform and process information), each with three stages. An organisation sits in a cell, and the useful question is which axis to move next.

## 2. The environment axis: how legible the organisation is

| | Crawl: scattered | Walk: verified | Run: contracted |
|---|---|---|---|
| **Platform identity and ownership** | Several catalogues, CMDBs and spreadsheets; owners stale; "the person who knows" is the directory | One platform card per platform with a named owner and a verified-on date; unverified cards expire | Cards are generated from the systems themselves where possible, verified by owners where not |
| **Intake** | Forms, tickets, emails and meetings, different per platform; intake is a funded demand in someone else's portfolio | Each platform's intake is described in one place in a common shape: what it needs, what it checks, who approves | Intake is a machine-readable contract (schema) that accepts a request from an agent acting for a person, runs its checks, returns status and records the decision |
| **Gates** | Criteria known to the reviewers; evidence requests arrive by email; wait times unmeasured | Each gate's criteria and evidence list are published and checkable; applicability is a screening (like the privacy two-of-nine) | Data gates accept evidence packets and decide by policy; judgement gates publish their intake and lead time; decisions are recorded with evidence |
| **Calendars and lead times** | In people's heads and slide decks | Release trains, freezes and planning windows published; lead times measured per platform and gate | Calendars and lead times are data the agent reads and the sequence is computed from them |
| **Decisions and history** | Slack threads, meeting notes, a RAID log updated when there is time | Decision records, small and numbered, with owner and source; a session of record per feature | Decisions written automatically at decision time, linked to evidence, audit-grade |
| **Agent identity** | None; the agent runs as a person's login | Agent identity with a sponsor; read access scoped per session | Delegation from the requester, recorded on every request; platforms accept agent-submitted requests under policy |
| **Evidence today** | The default state in the sources: [NHS onboarding](../../research/sources/nhs-england-nrl-onboarding-guidance.md), [Dingsøyr et al.](../../research/sources/arxiv-dingsoyr-coordinating-multi-team-programs.md), [Herbsleb and Grinter](../../research/sources/herbsleb-grinter-conways-law-revisited.md) | ING's "owner, contract, version, lifecycle, SLO, unit cost" per service ([ING](../../research/sources/techzine-nardiello-ing-decade-cloud-native.md)); Stripe's owner-verified docs; OpsLevel's inferred-then-confirmed owners ([OpsLevel](../../research/sources/opslevel-docs-service-detection.md)) | Pieces exist: Backstage template schemas ([Backstage](../../research/sources/backstage-docs-writing-templates.md)); Entra agent access packages ([Entra](../../research/sources/microsoft-entra-agent-access-packages.md)); pipeline change approval ([ServiceNow](../../research/sources/servicenow-docs-devops-change-velocity-approval.md)); NAB's "no form, no change board" ([NAB](../../research/sources/itnews-nab-cast-cloud-controls.md)). No platform found has all of it |

## 3. The agent axis: what the agent can do and how much unaided

| | Crawl: reads, drafts, proposes | Walk: submits and tracks under gates | Run: acts within policy |
|---|---|---|---|
| **Discovery (V1)** | Draws the map from whatever it can read; every edge sourced or flagged unverified; the "could not find" list is a first-class output | Map plus confidence; disagreements routed to owners as the smallest question; owner answers close flags | Map is largely generated from contracts and catalogues; the agent's attention goes to the exceptions |
| **Intake (V2)** | Pre-fills each platform's form from the spec; a person submits | Submits to platforms whose intake accepts agent requests, on behalf of a named person; a person approves | Submits and, where policy allows, receives automatic approval for routine requests; exceptions to people |
| **Sequencing (V3)** | Proposes an order with assumptions tagged; no dates it cannot source | Computes the sequence from published calendars; re-plans and notifies affected owners once; a person accepts moves to commitments | Re-plans within agreed bounds; commitments outside bounds go to people |
| **Routing and asking (V4)** | Drafts asks; a person sends | Posts asks as itself on behalf of the requester; chases by rule; escalates on timeout | Earned autonomy per channel from a weekly labelled sample |
| **Governance evidence (V5)** | Pre-screens applicability from published criteria; pre-fills packets; never submits | Submits packets to data gates; prepares judgement gates for a person; first-line only | Routine data-gate requests approved by policy; audit trail automatic |
| **Write-back (V6)** | Every answer written back as provisional with owner, date, source; a person verifies | Verification routed to owners; unverified entries expire; platform cards in the standard shape | Cards and decisions largely generated; the agent curates exceptions and measures freshness |
| **Portfolio signal (V7)** | None; one session at a time | Across sessions: lead time per platform and gate; where waiting happens | Feeds platform roadmaps and governance redesign; gates that never say no are visible |
| **Rights and checks** | Agent proposes, human decides, everywhere; deterministic checks on the artefacts | Rights per task class; separation of duties by identity; fail-closed checks before every side effect | Earned autonomy, tiered by risk; a labelled sample reviewed weekly; a person on every merge of a standard |

The seven dimensions of the project's skill-spectrum guide apply per value and per stage; [04-destination.md](04-destination.md) sets them for the run stage, and the crawl stage is simply "rights: propose; stance: ask; check: deterministic on the artefact; record: everything, provisional".

## 4. The cells that matter

Nine cells exist; four matter.

**Crawl agent, crawl environment (where almost every large regulated organisation starts).** The agent reads scattered, stale records and tribal threads, so its map is partial and its confidence low. Its value comes from three things it can do without legibility: it produces the first dependency map with an explicit "could not find" list, it forces every answer it gets into a standard shape with an owner and a date, and it measures how long each ask took. This is the cell the working hypothesis is about; section 5 tests it.

**Crawl agent, walk environment (an organisation that invested in a verified catalogue before an agent).** The agent's map is good on day one, which is the Stripe pattern: verify first, then put the bot over it. The risk is that the verification effort stalls without a consumer; an agent that reads the cards is the reason to keep them current.

**Walk agent, walk environment (the target for a first serious deployment).** The agent submits and tracks under human gates, writes back with owner verification, and the organisation has platform cards, published intake descriptions and measured lead times for the platforms the agent touches. This is where the film 13 story sits, and where the independent evidence on targeted chasing ([Nudge](../../research/sources/arxiv-maddila-nudge-overdue-pull-requests.md)) and recorded peer approval ([DORA 2019](../../research/sources/dora-state-of-devops-2019.md)) applies.

**Run agent, run environment (the destination in [04](04-destination.md)).** Contracts, policy-decided routine intake, automatic decision records, portfolio signal. No organisation found is here; the pieces are shipping separately.

Two cells are traps. **Run agent, crawl environment** is an agent allowed to act on records nobody trusts: the ING risk-scoring result ([Kapel et al.](../../research/sources/arxiv-kapel-ing-change-incident-prediction.md): near-chance scoring on half-empty fields) is what that looks like. **Run environment, crawl agent** is contracts and schemas nobody's agent reads, which is the llms.txt result.

## 5. the working hypothesis, tested

The hypothesis: an early-stage agent in a limited-context environment creates value by driving process standardisation while aggregating and curating context about dependencies, processes and platforms, and that work compounds into the later stages.

### What supports it

1. **Capture as a by-product of work is the pattern that has worked.** Stripe's owner-verified documentation, Shopify River's corrections ("will never have that mistake again"), Ramp Glass's user edits: in each, the context got better because an agent was using it and people corrected it in the flow of work, not because a documentation project was run. The project's earlier teardowns reached the same conclusion: the need for context creation is well supported; a standalone context-creation agent is not ([Stripe teardown](../competitive-teardown-stripe-knowledge-agents/00-teardown-summary.md)). A dependency agent is a strong by-product capturer because every dependency it chases produces an answer worth keeping.
2. **A clearly understood process is itself worth something.** DORA 2019 found a clearly understood change process made respondents 1.8 times more likely to be elite, separate from the finding that external approval hurt ([DORA 2019](../../research/sources/dora-state-of-devops-2019.md), independent). An agent that makes each platform's intake and each gate's criteria explicit, in one shape, is producing that understanding.
3. **The cross-team process is often undefined, so there is something to standardise.** Banks that copied tribes and squads inherited a model with no common cross-team process ([Lee](../../research/sources/jeremiahlee-failed-squad-goals.md), anecdote; [TBC Bank](../../research/sources/thoughtworks-tbc-bank-agile-transformation.md), vendor). Across 42 large-scale agile cases, integrating non-development functions was the top challenge ([Dikert et al.](../../research/sources/jss-dikert-large-scale-agile-transformations.md), independent).
4. **The measurement nobody has is cheap for the agent to produce.** No source publishes an intake-to-production lead time for any internal platform in a regulated organisation ([02-challenges.md](02-challenges.md)). An agent that times its own asks produces that number as a side effect, and the FCA explicitly asks firms to "invest in estate discovery to understand dependencies before designing change" ([FCA](../../research/sources/fca-implementing-technology-change.md), regulator).
5. **Inferred-then-confirmed is proven for ownership.** OpsLevel suggests owners from commit history and a human accepts; Azure routes incidents at 82.9% F1 as a recommender ([OpsLevel](../../research/sources/opslevel-docs-service-detection.md); [DeepTriage](../../research/sources/arxiv-pham-deeptriage-incident-routing.md)). A crawl agent proposing owners and asking them to confirm is this pattern applied to platforms.
6. **The regulatory direction is the same.** EU DORA requires the dependency map as a record; the ESAs' dry run shows firms cannot yet produce it cleanly ([ESAs](../../research/sources/esas-dora-dry-run-register-of-information.md)). An agent that aggregates and curates dependency context is building the artefact regulation already demands.

### What weighs against it, and what it means for the design

1. **Curation costs the scarce resource: owners' attention.** Managers already spend over half an hour a day answering questions ([Stack Overflow 2024](../../research/sources/stackoverflow-dev-survey-2024-professional-developers.md)); bot requests get switched off when untargeted ([Dependabot](../../research/sources/arxiv-he-dependabot-exploratory-study.md); [Wessel](../../research/sources/arxiv-wessel-dont-disturb-me-bots.md)). A crawl agent that floods owners with verification requests will be ignored, and the context will not improve. **Design consequence:** verification requests ride on real asks. The agent asks an owner to confirm a card only when it is already asking them something the feature needs, and it asks the smallest question. The Nudge result (60% faster resolution, 73% positive) came from suppressing noise and naming the blocker.
2. **An agent cannot verify what only an owner knows.** It can find that the runbook and the catalogue disagree; it cannot say which is right. Standardisation without owners is a form nobody filled. **Design consequence:** every write-back is provisional until a named person verifies it, and unverified entries expire. The value of a crawl agent is bounded by the share of owners who answer, so that share is the metric to watch from week one.
3. **Standardisation can be imposed badly.** A standard shape for platform cards and asks is useful only if the platform teams accept it. The Verify case shows a shared thing failing on fit and mandate ([NAO](../../research/sources/nao-investigation-into-verify.md)); the platform doctrine says "compelling, not mandated" ([Bottcher](../../research/sources/fowler-bottcher-what-i-talk-about-platforms.md)), and the regulated reality needs both ([02](02-challenges.md), section 3.3). **Design consequence:** the standard is the agent's output format first, which costs the platform team nothing; it becomes the platform's input format only when the platform team sees its own asks arriving in it and prefers that to the alternative.
4. **The dependencies that hurt most are the hardest to standardise.** Support functions and external parties ([Tkalich et al.](../../research/sources/arxiv-tkalich-critical-dependencies-cse.md)). A crawl agent will standardise the system-to-system dependencies first because they are easiest, which is not where the value is. **Design consequence:** the dependency-type checklist in [01](01-dependency-management-today.md) is applied to every map, so the process, approval and third-party rows are visibly empty rather than absent.
5. **Compounding is asserted, not measured.** No source measures the rate at which context improves under agent use, or the decay rate of ownership records. Stripe reports a steep drop in the documentation complaint, Shopify reports corrections sticking, both first-party and unquantified. **Design consequence:** the MVP must measure the verification rate, the staleness rate and the reuse rate (how often a later session reads an entry an earlier one wrote), because those are the numbers that would show compounding, and nobody has them.

### Verdict

The hypothesis holds, with a condition and a correction. It holds because by-product capture is the pattern that worked at the beacons, because a clearly understood process has independent evidence behind it, because the cross-team process in these organisations is often undefined, and because the measurement the agent produces is one nobody has. The condition is that verification must ride on real asks, as the smallest question, or the owners who are the bottleneck will switch the agent off. The correction is that "driving process standardisation" should be read as "producing a standard shape that platforms adopt because the asks already arrive in it", not as the agent imposing a process; the Verify failure is what imposition looks like. Whether the value compounds is the thing the MVP should be designed to measure.

## 6. What moves an organisation to the next stage

| From | To | What moves it | Evidence or reasoning |
|---|---|---|---|
| Crawl environment | Walk environment | A consumer that reads the records (an agent) plus owner verification with expiry; one card schema; lead times measured from real asks; a session of record per feature | Stripe verified first, then put the bot over it ([Stripe](../../research/sources/stripe-sessions-2024-10x-engineer-panel.md)); OpsLevel's suggest-then-confirm ([OpsLevel](../../research/sources/opslevel-docs-service-detection.md)); CMDB health metrics exist to be acted on ([ServiceNow](../../research/sources/servicenow-cmdb-health-kpis-metrics.md)) |
| Walk environment | Run environment | Platform teams publish intake as a schema with approvers and policy, because asks already arrive in that shape; data gates accept evidence packets; agent identity with sponsors; decisions recorded automatically | The intake rung is already the most machine-readable ([Backstage templates](../../research/sources/backstage-docs-writing-templates.md), [Kratix](../../research/sources/kratix-docs-promises-intro.md)); identity providers now support agent principals ([Entra](../../research/sources/microsoft-entra-agent-access-packages.md)); pipeline change approval is proven in banks ([NAB](../../research/sources/itnews-nab-cast-cloud-controls.md), [CBA](../../research/sources/itnews-cba-production-more-often-fewer-incidents.md)) |
| Crawl agent | Walk agent | Rights per task class; agent identity; a labelled sample of its asks reviewed weekly; chase rules in code; fail-closed checks before submission | The skill-spectrum guide's earned-autonomy pattern ([design guide](../research-skill-rigidity-spectrum/03-design-guide.md)); Nudge's chase rules ([Nudge](../../research/sources/arxiv-maddila-nudge-overdue-pull-requests.md)) |
| Walk agent | Run agent | Policy-decided routine intake on an easier population, tiered by risk, with reverts and incidents measured; the walk environment must already exist | RADAR: risk-stratified auto-approval on an easier population, measured ([Adams et al.](../../research/sources/arxiv-adams-meta-radar-low-risk-review.md)); the ING warning on scoring ([Kapel et al.](../../research/sources/arxiv-kapel-ing-change-incident-prediction.md)) |

The rule the table implies: **move the environment axis one step ahead of the agent axis.** A run agent in a walk environment acts on records it cannot trust; a run environment with a crawl agent is contracts nobody reads. The agent is the reason the environment improves, and the environment is the limit on what the agent may do.

## 7. What this model does not claim

It does not claim the stages are sequential for every platform; an organisation will have platforms at every stage at once, and the agent's map should show which stage each platform is at. It does not claim timescales; no source gives any. It does not claim that run is right for every gate; judgement gates (model validation, privacy assessment, threat modelling) may stay at walk by design, because independence rules keep the decision with a person. And it does not claim the compounding effect, which it asks the MVP to measure.
