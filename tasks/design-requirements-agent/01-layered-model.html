The requirements agent, in four layers

An agent that takes a high-level idea from a product manager, or anyone doing the product task, and shapes it into the complete set of requirements the change must meet to ship in a large, platform-centric, regulated organisation. It reads unstructured context, cites governed data products, runs a fixed set of skills, and produces artifacts that a person owns and the dependency agent picks up.

Out of scope: the dependency agent

Takes the validated register and finds which platforms, capabilities, data and processes can satisfy each requirement, what onboarding each takes, and who must act.

What comes back: a requirement whose delivery path changes its wording, or a constraint the platform imposes. The requirements agent re-screens what changed.

Rules that hold across every layer
  1. Read before asking. A person is asked only what the context cannot answer.
  2. No requirement without a source: a governed record, a cited document, or a named person's answer.
  3. Every domain the screen opens ends with requirements or with "none, because" and the criterion.
  4. Everything the agent infers is provisional until a named validator confirms it.
  5. It classifies which obligations apply. Risk assessment and sign-off stay with the people whose independence the rules require.
  6. It never ratifies its own work and never grades it in the same context.
  7. It may show how an obligation is easier to meet. It never advises skipping one.
  8. Implementation is left open: standards any build must meet are requirements; which platform meets them is the dependency agent's job.
